# Sprint 01 Database Design: Multi-Tenant Foundation

- Status: Proposed
- Sprint: 01
- Scope: PostgreSQL tenant foundation
- Related ADR: ADR-001 Architecture Vision
- Related Requirements: Sprint 01 Multi-Tenant Foundation Requirements
- Related Technical Design: Sprint 01 Multi-Tenant Technical Design

## 1. Purpose

This document defines the initial PostgreSQL schema for the multi-tenant
foundation.

The design must support:

- Shared database
- Shared schema
- TenantId-based isolation
- Global tenant lookup
- Future tenant-owned business tables
- EF Core migrations
- PostgreSQL-compatible constraints and indexes

This sprint introduces only the tenant foundation schema.

It does not introduce:

- Users
- ASP.NET Core Identity tables
- Tenant memberships
- Projects
- Tasks
- Documents
- Audit logs
- Subscriptions
- Billing
- OCR-related tables

## 2. Database Conventions

### 2.1 Database Engine

PostgreSQL 17 is the local development database.

The application must not depend on PostgreSQL 17-specific features unless
explicitly justified.

The schema should remain compatible with managed PostgreSQL services.

### 2.2 Schema

Application tables will use the PostgreSQL schema:

public

A separate application schema may be considered later if justified.

### 2.3 Naming Convention

Database identifiers will use snake_case.

Examples:

- tenants
- normalized_slug
- created_at_utc
- updated_at_utc
- tenant_id

Primary keys will use:

pk_{table_name}

Foreign keys will use:

fk_{source_table}_{target_table}_{column_name}

Unique constraints or indexes will use:

uq_{table_name}_{column_names}

Indexes will use:

ix_{table_name}_{column_names}

Check constraints will use:

ck_{table_name}_{rule_name}

### 2.4 Identifier Type

Primary keys and tenant identifiers will use PostgreSQL uuid.

EF Core type:

Guid

IDs must be generated by the application unless a later ADR defines a
database-generated strategy.

### 2.5 Time Type

UTC timestamps will use PostgreSQL:

timestamp with time zone

EF Core type:

DateTime

Application code must write UTC values.

The database and application must not rely on local server time zones.

### 2.6 Text Encoding

The database uses UTF8.

Turkish characters and multilingual tenant data must be stored without
loss.

Locale selection must not be treated as a character storage limitation.

## 3. Tenants Table

### 3.1 Table Name

public.tenants

### 3.2 Purpose

Stores one row for each organization or workspace using the SaaS platform.

This table is tenant-independent.

It must not contain a tenant_id column.

### 3.3 Columns

#### id

- PostgreSQL type: uuid
- EF Core type: Guid
- Nullable: No
- Primary key: Yes
- Generated by application: Yes

#### name

- PostgreSQL type: character varying(200)
- EF Core type: string
- Nullable: No
- Maximum length: 200

The name is the human-readable organization or workspace name.

Leading and trailing whitespace must be removed before persistence.

#### slug

- PostgreSQL type: character varying(100)
- EF Core type: string
- Nullable: No
- Maximum length: 100

The slug is the canonical URL-safe tenant identifier.

The persisted value must already be normalized.

The field must not preserve a second unnormalized representation.

#### is_active

- PostgreSQL type: boolean
- EF Core type: bool
- Nullable: No
- Default: true

Inactive tenants cannot perform normal tenant-owned operations.

#### created_at_utc

- PostgreSQL type: timestamp with time zone
- EF Core type: DateTime
- Nullable: No

Set by application persistence logic.

#### updated_at_utc

- PostgreSQL type: timestamp with time zone
- EF Core type: DateTime
- Nullable: No

Set by application persistence logic.

## 4. Tenant Slug Decision

Only one persisted slug column will be used:

slug

A separate normalized_slug column will not be stored.

Reason:

- The slug itself is canonical and normalized
- Duplicate persisted representations create consistency risk
- The application can normalize input before persistence
- PostgreSQL can enforce uniqueness on the canonical slug

Normalization rules:

- Trim whitespace
- Lowercase invariant
- Convert whitespace to hyphens
- Remove unsupported characters
- Collapse repeated hyphens
- Remove leading and trailing hyphens

Examples:

"Example Workspace" -> "example-workspace"

"  ABC   Workspace  " -> "abc-workspace"

The application must reject a normalized slug that becomes empty.

## 5. Constraints

### 5.1 Primary Key

Constraint:

pk_tenants

Columns:

id

### 5.2 Required Columns

The following columns are NOT NULL:

- id
- name
- slug
- is_active
- created_at_utc
- updated_at_utc

### 5.3 Unique Slug

A globally unique index will enforce tenant slug uniqueness.

Index name:

uq_tenants_slug

Column:

slug

Unique:

Yes

Rationale:

Tenant slugs identify tenants globally in the current platform design.

If custom domains or region-specific tenant namespaces are introduced later,
this decision may be reviewed.

### 5.4 Name Validation

A database check constraint will reject empty or whitespace-only names.

Constraint name:

ck_tenants_name_not_blank

Conceptual expression:

length(btrim(name)) > 0

### 5.5 Slug Validation

A database check constraint will reject empty slugs.

Constraint name:

ck_tenants_slug_not_blank

Conceptual expression:

length(btrim(slug)) > 0

A second check constraint may enforce the allowed slug format.

Constraint name:

ck_tenants_slug_format

Conceptual expression:

slug ~ '^[a-z0-9]+(?:-[a-z0-9]+)*$'

This allows:

- Lowercase ASCII letters
- Numbers
- Single hyphens between segments

This intentionally rejects:

- Uppercase letters
- Spaces
- Turkish characters inside canonical URLs
- Leading or trailing hyphens
- Repeated hyphens
- Underscores

Turkish tenant names remain fully supported in the name column.

## 6. Indexes

### 6.1 Tenant Slug Lookup

Index:

uq_tenants_slug

Columns:

slug

Unique:

Yes

Supports:

- Tenant resolution by slug in future authentication flows
- Tenant onboarding uniqueness checks

### 6.2 Active Tenant Lookup

Do not add a standalone index on is_active in the initial migration.

Reason:

A boolean column with low cardinality is usually not selective enough to
justify a separate index for the expected workload.

If future operational queries frequently scan active tenants, a partial index
may be evaluated using measured query plans.

## 7. Initial SQL Shape

The expected conceptual PostgreSQL structure is:

CREATE TABLE public.tenants
(
    id uuid NOT NULL,
    name character varying(200) NOT NULL,
    slug character varying(100) NOT NULL,
    is_active boolean NOT NULL DEFAULT true,
    created_at_utc timestamp with time zone NOT NULL,
    updated_at_utc timestamp with time zone NOT NULL,
    CONSTRAINT pk_tenants PRIMARY KEY (id),
    CONSTRAINT ck_tenants_name_not_blank
        CHECK (length(btrim(name)) > 0),
    CONSTRAINT ck_tenants_slug_not_blank
        CHECK (length(btrim(slug)) > 0),
    CONSTRAINT ck_tenants_slug_format
        CHECK (slug ~ '^[a-z0-9]+(?:-[a-z0-9]+)*$')
);

CREATE UNIQUE INDEX uq_tenants_slug
    ON public.tenants (slug);

This SQL is conceptual.

The EF Core migration remains the source-controlled implementation.

## 8. Future Tenant-Owned Table Rules

Every tenant-owned table must include:

tenant_id uuid NOT NULL

Every tenant_id column must reference:

public.tenants(id)

Unless a later ADR explicitly permits otherwise.

### 8.1 Foreign Key

Recommended behavior:

ON DELETE RESTRICT

Reason:

Deleting a tenant must not cascade-delete all tenant data accidentally.

Tenant deletion should be a controlled lifecycle operation.

### 8.2 Tenant Index Prefix

Tenant-owned tables must normally have indexes beginning with tenant_id when
queries are tenant-scoped.

Examples:

ix_tasks_tenant_id_created_at_utc

uq_tasks_tenant_id_task_number

uq_projects_tenant_id_project_code

Indexes must be designed according to actual query patterns.

Do not add redundant standalone tenant_id indexes when an existing composite
index already covers the required access pattern.

### 8.3 Tenant-Scoped Uniqueness

Business identifiers unique inside a tenant must use composite unique
constraints.

Examples:

- tenant_id + task_number
- tenant_id + project_code
- tenant_id + document_reference

Business identifiers must not be globally unique unless required by the
business domain.

## 9. Tenant Deletion Strategy

Physical tenant deletion is not part of this sprint.

The tenants table will not include deleted_at_utc or is_deleted.

The application must treat tenant deletion as unsupported until a later ADR
defines:

- Retention requirements
- Archival
- Legal obligations
- Data export
- Deactivation
- Permanent deletion workflow

The current lifecycle control is:

is_active

Deactivation is reversible and does not delete data.

## 10. Seed Data

The initial migration must not seed a production tenant.

Reason:

- Production data should not be introduced by schema migration
- Tenant creation is a business operation
- Seeded IDs can create environment coupling

For local development, a tenant may be created manually using:

- A reviewed SQL script
- A future development-only bootstrap command
- pgAdmin
- psql

Any local development script must use a fixed documented Guid only if tests or
manual development workflows require deterministic data.

## 11. Migration Scope

The initial migration name should be:

InitialTenantFoundation

The migration must include only:

- tenants table
- primary key
- required columns
- default value for is_active
- slug unique index
- name check constraint
- slug non-blank check constraint
- slug format check constraint

The migration must not include:

- Identity tables
- Business module tables
- Seeded tenants
- Stored procedures
- Triggers
- Row-level security
- Extensions
- Automatic timestamps
- Audit log tables

## 12. Migration Location

Migrations will be stored in:

src/backend/SaaSPlatform.Infrastructure/Persistence/Migrations

Migration assembly:

SaaSPlatform.Infrastructure

Startup project:

SaaSPlatform.WebApi

Future command:

dotnet ef migrations add InitialTenantFoundation `
  --project src/backend/SaaSPlatform.Infrastructure `
  --startup-project src/backend/SaaSPlatform.WebApi `
  --output-dir Persistence/Migrations

Migration execution:

dotnet ef database update `
  --project src/backend/SaaSPlatform.Infrastructure `
  --startup-project src/backend/SaaSPlatform.WebApi

Migrations must be reviewed before database update.

## 13. Connection Configuration

The application connection string key is:

ConnectionStrings:PostgreSql

A real connection string must not be committed.

Example only:

Host=localhost;Port=5432;Database=saas_platform_dev;Username=saas_platform_app;Password=CHANGE_ME

Local secrets should use .NET user-secrets.

The committed appsettings files must not include real passwords.

## 14. Local Databases

Recommended local databases:

Development:

saas_platform_dev

Integration tests:

saas_platform_test

Recommended application role:

saas_platform_app

The application should not normally connect using the postgres superuser.

Separate database users for development and tests may be introduced later if
required.

## 15. Database Permissions

The application database role should follow least privilege.

During early local development, saas_platform_app may own the development
database to simplify migrations.

Before production deployment, permissions must be reviewed to separate:

- Migration privileges
- Runtime application privileges
- Administrative privileges

The runtime production application should not have unnecessary schema
administration privileges.

## 16. Row-Level Security Decision

PostgreSQL Row-Level Security is not included in Sprint 01.

Current enforcement layers are:

- Trusted tenant resolution
- EF Core global query filters
- SaveChanges tenant validation
- Foreign keys
- Composite uniqueness constraints
- Integration tests

RLS may be evaluated later as an additional defense-in-depth layer.

Reasons for deferral:

- Additional operational complexity
- Session tenant context management
- Migration and background job implications
- Need for carefully designed connection pooling behavior
- Current scale does not yet justify the added complexity

RLS is not rejected permanently.

## 17. Data Retention and Backup

Detailed retention and backup policies are outside this sprint.

The schema must not block future:

- Point-in-time recovery
- Tenant export
- Tenant archival
- Legal retention
- Anonymization
- Soft deletion

No tenant data will be introduced in this migration.

## 18. Validation Queries

After applying the migration, the following checks should be possible:

Verify table:

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name = 'tenants';

Verify columns:

SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'tenants'
ORDER BY ordinal_position;

Verify indexes:

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'tenants';

Verify constraints:

SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.tenants'::regclass;

## 19. Test Cases

Database-related tests must validate:

1. Tenant slug uniqueness is enforced.
2. Empty tenant names are rejected.
3. Empty tenant slugs are rejected.
4. Invalid slug formats are rejected.
5. Turkish characters are stored correctly in tenant names.
6. UTC timestamps can be persisted.
7. Tenant rows do not require tenant_id.
8. Future tenant-owned entities can reference tenants through uuid foreign
   keys.

## 20. Risks

### Risk: Slug Normalization Mismatch

Application normalization and database validation could diverge.

Mitigation:

- One canonical normalization implementation
- Unit tests
- Database format constraint
- Integration tests

### Risk: Tenant Deletion Causes Data Loss

Mitigation:

- ON DELETE RESTRICT
- No tenant deletion workflow in this sprint
- is_active for lifecycle control

### Risk: Over-Indexing

Mitigation:

- Add indexes from measured query patterns
- Avoid standalone indexes without clear use
- Review PostgreSQL query plans as modules are added

### Risk: Using Superuser Credentials

Mitigation:

- Use saas_platform_app
- Store credentials in user-secrets
- Review production privileges separately

### Risk: Migration Includes Unrelated Features

Mitigation:

- Keep InitialTenantFoundation migration narrowly scoped
- Review generated SQL before applying
- Reject unexpected tables or dependencies
